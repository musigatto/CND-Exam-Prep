## The scale problem _(Mod 15 p117)_

Printed as the "Why Centralized Logging?" callout list:

- **Virtually every device or application on the network has the capability to generate its logs in
  some form or another**
- Each of these devices can generate **thousands to tens of thousands of events per day** in their
  log files
- Analyzing these log files **can overwhelm staff who monitor and analyzes it**
- **He/she has hundreds of log files to choose from** to detect a sign of an incident

The prose on the same page names what those events actually are — an organization "that runs on a
number of devices and uses several applications" generates them: **user session activity**, **all
access attempts (including failures)**, **the connection of external devices to the organization's
network**, and other events. Analyzing all of them "would be a difficult task for the staff who
monitors and analyzes them."

## What centralization buys _(Mod 15 p117)_

- Maintains the records of **all the log files in one place**, "where they can be **accessed,
  monitored, or scheduled for alerts against threats**"
- Provides **deep insights about the network events** — "**what kind of event it is, when and why it
  is generated**" — "without any hassle"
- Works **even if the staff is not monitoring the logs**: the centralized logging application can
  "**review the logs, pick out suspected events, and alert the network defender through various
  means**" → "helps the management **respond faster** and take the required steps"

## Reasons for adopting centralized logging over local logging _(Mod 15 p117)_

The page's own list, verbatim:

1. "With centralized logging, **log analysis outside the production environment** is possible."
2. "Centralized logging makes it easy to **search for a single transaction that has been processed
   across multiple application servers**."
3. "Centralized logging is a **storage efficient** technique that helps in **saving costs and
   reducing disk I/O on application servers**."

Three levers, and they are the ones to remember: **analysis decoupled from production**, **one
transaction searchable across many servers**, **storage/cost off the application server**.

## Centralized logging = CLM _(Mod 15 p118)_

> "Centralized logging or **centralized log management (CLM)** is a logging solution that can
> **collect all the log files generated by different devices and applications on the network and
> push it to one central and accessible location**. It not only collects log information but also
> supports **aggregating, monitoring, analyzing, and reviewing logs for any anomalies**."

The callout on the page states the same in two lines: logs from different devices and applications
"are collected to the one central location", which "helps staff to **clearly and quickly monitor,
analyze, and review the logs for any anomalies**".

### CLM capabilities _(Mod 15 p118)_

Printed list:

| # | Capability (as printed) |
|---|---|
| 1 | "It allows a **scan of the entire network in one location** and obtain a **360-degree view** of the activities that are going on in the network." |
| 2 | "It **generates alerts based on the metrics defined on the log**." |
| 3 | "It allows **sharing of the dashboard and log information with others**." |
| 4 | "It allows **access to the important data from logs files**." |
| 5 | "It **applies retention policies** so that a specific log can be available at the right time." |
| 6 | "It provides a **large amount of space for storing and taking a backup of historical data**." |
| 7 | "It provides a **deep understanding of the events** and helps the staff answer questions such as **who, what, when, and where** an event occurred." |
| 8 | "It **improves the security of the network**." |
| 9 | "It allows **access to data in seconds instead of hours, weeks, or even days**." |

The figure on the same page condenses these into four: **stores logs from different sources to one
central location** · **easily access the important data from logs files** · **generates alerts based
on metrics defined in the log** · **quickly share the dashboard and log information with others**.

### What CLM actually does with a log file _(Mod 15 p118)_

> "CLM processes the log files by **collecting, transporting, storing, and analyzing** them and then
> **decides whether to send an alert or not, based on the configured rules**."

```
collect → transport → store → analyze → alert decision (configured rules)
```

Alert delivery: "**emails, help desk tickets, or in any other way the user prefers**."

## Local vs centralized _(Mod 15 p117–118, contrast with p115)_

The module closes LO#07 on web servers with "**monitoring and analyzing log files of different
devices locally can be a difficult task. Centralized logging helps you to simplify the process**"
_(Mod 15 p115)_. The local, per-device approach is catalogued in
[[15-LO01c-Typical-Log-Format-and-Logging-Approaches]]; centralized logging is the answer to it.

| | Local logging | Centralized logging (CLM) |
|---|---|---|
| Where records live | on each device, in its own path and format | one central and accessible location |
| Who reads them | a person on the device | an application, plus a person |
| Scale | hundreds of log files to choose from _(p117)_ | one location, 360-degree view _(p118)_ |
| Coverage of one transaction | per-server only | searchable across multiple application servers _(p117)_ |
| Analysis site | the production environment | outside the production environment _(p117)_ |
| Disk cost | on the application server | reduced on the application server _(p117)_ |
| Unattended | nobody is watching | app reviews logs, picks out suspected events, alerts the defender _(p117)_ |
