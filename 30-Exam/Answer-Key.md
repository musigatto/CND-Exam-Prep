# Answer Key

> [!info] Convention
> `Q#### → Answer` + one-line justification citing `Module NN · Topic`.

## Module 01
- Q001 - **A** - Module 01 · Essential Terminologies: *Risk = Asset + Threat + Vulnerability*.
- Q002 — **B** — *DHCP starvation* floods the server with spoofed-MAC requests using tools such as Gobbler, exhausting the IP pool → DoS (Module 01 · Network-level Attacks).
- Q003 — **C** — *Session side-jacking* uses packet sniffing to intercept session cookies when the site does not use SSL/TLS for the **entire** session (Module 01 · Application-level Attacks — Session Hijacking).
- Q004 — **B** — *Reactive approach* is complementary to preventive and includes security monitoring methods such as IDS, SIMS, TRS, and IPS (Module 01 · Continual/Adaptive Security Strategy).
- Q005 — **B** — The 11 Enterprise tactics are derived from the later Cyber Kill Chain stages: exploit, control, maintain, and execute (Module 01 · Hacking Methodologies — MITRE ATT&CK).

## Module 02
- Q006 — **B** — Compliance hierarchy: *Frameworks → Policies → Standards → Procedures → Guidelines* (Module 02 · Regulatory Frameworks Compliance).
- Q007 — **A** — A *data controller* alone or jointly determines purposes/means of processing; a *data processor* processes on the controller's behalf; controllers/processors in the EU must comply with GDPR (Module 02 · Regulatory Frameworks — GDPR).
- Q008 — **D** — *Prudent*: all services blocked by default, network defender individually enables safe/necessary services, maximum security + everything logged (Module 02 · Security Policy — Internet Access Policies).
- Q009 — **B** — Asset categorization groups by type, usage, location, owner/department, lifecycle stage, vendor/manufacturer, criticality, and license type (Module 02 · Asset Management — ITAM process).
- Q010 — **A** — A *Secret*-level user has "access to secret + confidential + restricted + unclassified" but **NOT** top secret; only Top Secret users access everything (Module 02 · Security Awareness Training — Data Classification).

## Module 03
- Q011 — **C** — *Research* honeypots evaluate the attacker's steps precisely to build countermeasures; *production* honeypots look real next to production servers to identify attackers (Module 03 · Essential Network Security Solutions — Honeypot).
- Q012 — **C** — NAC checks AV presence/update, configured firewall or IPS, viruses, and OS updates — a Wi-Fi password check is **not** listed (Module 03 · Essential Network Security Solutions — NAC).
- Q013 — **B** — *TACACS+* (Cisco) separates AAA and encrypts the entire client–server communication including the password; it is connection-oriented over **TCP port 49** vs RADIUS (UDP) (Module 03 · Essential Network Security Protocols — TACACS+).
- Q014 — **A** — *AH* authenticates the sender only; *ESP* authenticates the sender **and** encrypts the data (Module 03 · Essential Network Security Protocols — IPsec).
- Q015 — **C** — *UTM* combines firewall, IDS, anti-malware, spam filter, content filtering, DLP, and VPN in one appliance; a known drawback is single point of failure (Module 03 · Essential Network Security Solutions — UTM).

## Module 04
- Q016 — **B** — *Packet filtering* firewalls "work at the network level of the OSI model," checking each packet's header against rules; circuit-level works at the session layer and application-level at the application layer (Module 04 · LO02 Firewall Technologies).
- Q017 — **A** — Deployment *L1 (outside the perimeter firewall)* is tuned to least-sensitive attacks, "logs attack attempts only, no alerts"; L2 DMZ covers low–moderate, L3 backbone medium–high, L4 critical high-impact (Module 04 · LO12 NIDS Deployment Locations).
- Q018 — **A** — Because encrypted payloads can't be matched to signatures, the module advises placing "an IDS behind a VPN termination with SSL encryption" so traffic arrives decrypted (Module 04 · LO13 Dealing with False Negatives).
- Q019 — **C** — *Static* port security "allows only a single MAC address to be connected to a port"; sticky assigns per port (lost on reboot), dynamic is the CAM default (Module 04 · LO16 Switch Security Measures).
- Q020 — **D** — The *SDP controller* is "an authentication point that evaluates the policy and grants access to the client" and determines which client↔gateway pairs communicate; traffic tunnels only after controller approval (Module 04 · LO17 SDP Architecture and Components).

## Module 05
- Q021 — **B** — *Virtual service accounts* run each service under its own account/SID named `NT SERVICE\<service name>`, with password set and periodically changed by Windows (Module 05 · §5.3 Windows Security Features — Virtual Service Accounts).
- Q022 — **A** — `net user guest /active:No` disables the Guest account (guards against password-less/unauthenticated Internet access); policy variant: `Accounts: Guest account status` (Module 05 · §5.5 User Account and Password Management).
- Q023 — **A** — `sc config wuauserv start= auto` enables automatic-start of the Windows Update service (Module 05 · §5.6 Windows Patch Management).
- Q024 — **A** — *Just Enough Administration (JEA)* grants only needed cmdlets/scripts/functions via role capability files + session configuration files (Module 05 · §5.7 User Access Management).
- Q025 — **B** — DNSSEC guarantees *authenticity*, *integrity*, and *non-existence* of a domain name or type; it explicitly does **not** guarantee confidentiality or DoS protection (Module 05 · §5.10 Network Services and Protocol Security — DNSSEC).

## Module 06
- Q026 — **B** — `find / -perm +4000` shows *all files with SUID set* (`+2000` = SGID); `chmod a-s` removes the bit — a wrong SUID list is a privilege-escalation risk (Module 06 · §6.4 File Permissions — SUID/SGID).
- Q027 — **B** — the module's Table 6.5 maps *blocking an XMAS scan* to `iptables -A INPUT -p tcp --tcp-flags ALL ALL -j DROP`; the NULL/fragment rules are separate entries (Module 06 · §6.5 Host-based Firewall with iptables).
- Q028 — **B** — *Permissive* "prints warnings instead of enforcing"; *enforcing* applies the SELinux policy (blocks requests) and *disabled* loads no policy (Module 06 · §6.6 Security-Enhanced Linux modes).
- Q029 — **C** — Ubuntu minimal installation *removes approximately 80 packages* vs the default, restricting third-party/untrusted applications that may be vulnerable to new exploits (Module 06 · §6.2 Linux Installation — Minimal Installation).
- Q030 — **C** — Chroot SFTP: comment out the sftp Subsystem and append `Subsystem sftp internal-sftp` + `Match group sftponly` block (`ChrootDirectory /sftp/`, `X11Forwarding no`, `AllowTcpForwarding no`, `ForceCommand internal-sftp`) (Module 06 · §6.5 Setup Chroot SFTP).

## Module 07
- Q031 — **C** — *CYOD* lets employees select devices (laptops, smartphones, tablets) from a *company-approved list*; the company purchases the selected device (Module 07 · §7.1 Choose Your Own Device).
- Q032 — **C** — *System-based risks* cover vulnerabilities unintentionally introduced by manufacturers, e.g., in *SwiftKey keyboards* or mobile OSes; mitigation is regular device updates (Module 07 · §7.2 Risk and Challenge Categories).
- Q033 — **B** — *SaaS-based MDM* suits organizations that do not want to maintain on-site servers but still want management and admission; they can negate up-front cost by paying monthly/annual fees (Module 07 · §7.3 MDM Delivery Methods).
- Q034 — **D** — The guidelines list *remote wipe services* such as Find My Device (Android) and Find My iPhone / FindMyPhone (iOS) to locate/wipe lost or stolen devices (Module 07 · §7.4 Use Remote Wipe Services).
- Q035 — **C** — *Maximum failed password attempts* specifies how many wrong entries are allowed before the device wipes its data; the API also allows remote factory reset for lost/stolen devices (Module 07 · §7.5 Android Device Administration API).

## Module 08
- Q036 — **C** — *Device-to-Device*: connected devices interact directly via the Internet (often primarily directly) using Bluetooth, Z-Wave, Zigbee, or Wi-Fi (smart-home devices, wearables, ECG/EKG paired to smartphone) (Module 08 · §8.2 IoT Communication Models).
- Q037 — **D** — *Bluesnarfing* = via Bluetooth, exploit OBEX Push to access phone/Laptop data; *BlueBugging* = remote control of device (unrestricted access, AT commands, Internet connect, place calls) via OBEX Push profile / personal-area-network FTP (Module 08 · §8.4 Bluetooth Attacks).
- Q038 — **A** — *KillerBee* is the ZigBee/IEEE 802.15.4 exploitation toolkit: zbdump, zbconvert, zbreplay, zbstumbler, zbfind, zbinject, zbopenear (Module 08 · §8.4 ZigBee / IEEE 802.15.4 Attacks).
- Q039 — **C** — *SeaCat.io* gateway tunnel listens on **48101** (SeaCat mutual-TLS), with Nginx on 443 (Module 08 · §8.6 IoT Security Tools — SeaCat.io).
- Q040 — **B** — The *GSMA IoT Security Assessment* audits 8 areas: secure boot, storage, key management, over-the-air updates, app isolation, DDoS protection, user-data privacy, attack mitigation — *secure boot* is one of them (options A/C/D are NIST areas) (Module 08 · §8.7 GSMA IoT Security Guidelines).

## Module 09
- Q041 — **B** — *Whitelisting* = trust-centric, allow only approved, deny by default; *blacklisting* = threat-centric, allow by default, deny a list of known-bad programs; blacklist cons = never comprehensive, no zero-day defense, easily evadable (Module 09 · §9.1 Whitelisting/Blacklisting Approaches).
- Q042 — **C** — The SRP *hash rule* hashes the file so the rule applies wherever the file is located (even after rename/move); path rules break when the file moves, certificate rules use signing (not enabled by default), internet-zone rules apply only to .msi (Module 09 · LO01 Software Restriction Policy Rule Types).
- Q043 — **B** — *WDAG* runs Microsoft Edge in a hardened container: blocks websites from local storage, memory, installed apps, corporate network endpoints; prerequisites include 64-bit, ≥4 cores with virtualization + SLAT, ≥8 GB RAM (Module 09 · LO02 Windows Defender Application Guard).
- Q044 — **A** — Patch-management flow: *scan for new/missing patches → download to a central location → select the relevant client patch → test the patch → deploy if the test succeeds* (Module 09 · LO03 Application Patch Management).
- Q045 — **C** — WAF *limitations* include "cannot read database commands" → not complete web-app attack protection; it is not a substitute for user auth/input filtering, not set-and-forget, and offers no false-positive protection (Module 09 · LO04 WAF Limitations).

## Module 10
- Q046 — **A** — The module maps safeguards to the 3 data states: *in transit* → SSL/TLS and PGP/S-MIME email encryption; *in use* → authentication, memory encryption, strong identity, patching; *at rest* → encryption, password/tokenization, access control (Module 10 · LO01 Three States of Data).
- Q047 — **B** — *Always Encrypted deterministic* encryption produces the same ciphertext for the same plaintext, enabling equality lookups; randomized always produces different ciphertext (less predictable); TDE encrypts data at rest only and the engine holds keys (Module 10 · LO03 Always Encrypted).
- Q048 — **A** — Oracle data-masking F.A.S.T. = *Find → Access → Secure → Test*; discovery jobs find sensitive columns (CREDITCARDNUMBER, SSN 9-digit) before the masking definition/job "secures" them (Module 10 · LO05 Oracle Data Masking F.A.S.T.).
- Q049 — **B** — Oracle cold backup: *SHUTDOWN IMMEDIATE → STARTUP MOUNT → BACKUP DATABASE → ALTER DATABASE OPEN*; a closed database needs no archive logs, unlike the RMAN hot backup with ARCHIVELOG (Module 10 · LO06 Oracle Cold vs Hot Backup).
- Q050 — **B** — *Purging* (degaussing + Secure Erase) defends against laboratory attacks using signal-processing recovery; clearing/overwriting only counters keyboard-level convenience attacks (Module 10 · LO07 Data Destruction Techniques).

## Module 11
- Q051 — **B** — The single discriminator across the four approaches is *who performs the binary translation*. **Full** = the VMM (guest unaware; the VMM translates and forwards to the host OS); **OS-assisted / para** = the **guest OS** translates its own commands and the **VMM is not involved** in the request and response operations; **Hardware-assisted** = special CPU instructions, no translation step; **Hybrid** = the guest adopts para-functionality *and* the VMM still does binary translation (Module 11 · LO02 Virtualization Approaches).
- Q052 — **B** — *MAC flooding*: a large number of fake MAC addresses overflow the CAM table, so once it is full, traffic **without MAC entries floods out to all ports of the VLAN**, letting the attacker more easily view and retrieve traffic. DHCP starvation floods the DHCP server instead; an ARP attack poisons the ARP table to bind the attacker’s MAC to a legitimate IP; a spanning-tree attack wins root-bridge election and then installs and transmits junk data (Module 11 · LO03 VLAN Attacks).
- Q053 — **A** — The Data Plane has exactly three attack types: **Device Attack** (software/hardware vulnerabilities of the SDN switch — firmware, the **TCAM**), **Protocol Attack** (network-protocol vulnerabilities of the forwarding device), and **Side Channel Attack** (deducing forwarding policy, e.g. from packet-processing timing analysis). B and C name categories belonging to the Southbound API, Control Plane and Application Plane, not the Data Plane; D restates Device-Attack *targets* as if they were attack types (Module 11 · LO04 SDN Vulnerabilities and Attacks, Attacks by Component Impacted).
- Q054 — **A** — The five Docker native drivers are **Host** (uses the host networking stack), **Bridge** (a Linux bridge created on the host, managed by Docker), **Overlay** (container-to-container over the physical network infrastructure), **MACVLAN** (container interfaces bound to the parent host interface or sub-interfaces), and **None** (the container implements its own stack, isolated from the host’s). B substitutes a driver the module does not list, C reorders and adds `macvtap`, and D confuses a network driver with an **IPAM driver**, which the module treats as a separate class supplying default subnets and IP addressing (Module 11 · LO06 Docker Network Drivers, H·B·O·MAC·N).
- Q055 — **A** — A user may create or update a role only if they have **all the permissions contained in the role** and **at the same scope as the role** — **cluster-wide for a ClusterRole**, within the same namespace for a Role. B fails the same-scope test; C misreads the purpose of the RBAC API, which exists precisely to *block* privilege escalation through editing roles or role bindings and is enforced at the API level even when the RBAC authorizer is not in use; D inverts the rule (Module 11 · LO09 Kubernetes RBAC and API Server Hardening).

## Module 12
- Q056 — **C** — The five significant actors are consumer, provider, **carrier**, **auditor** and **broker**. The **cloud auditor** "independently examines the cloud service controls to express a corresponding opinion," and "audits verify adherence to standards by reviewing objective evidence." A audits the *controls*, not data in transit (that is the carrier's domain — the carrier "acts as an intermediary providing connectivity and transport services between the cloud service providers and cloud consumers"); a broker *combines services*; the consumer is the party that specifies QoS/security/remedies and that "renew[s] SLAs if security gaps are found" (Module 12 · §12.1 NIST Cloud Reference Architecture).
- Q057 — **D** — The four are **FIDO security keys · virtual authenticator apps · TOTP hardware tokens · TOTP hardware tokens for the AWS GovCloud (US) Regions**. B is the trap: **Thales** and **Hypersecu** are the *named providers* of TOTP hardware tokens (Thales for ordinary AWS accounts; Hypersecu for AWS GovCloud (US) accounts), not additional methods. A substitutes SMS/email OTP, which the module never lists. the module also separates the two *response* styles — virtual/hardware devices produce a code the user types, while U2F security keys respond when tapped and the sign-in completes automatically (Module 12 · §12.4 AWS IAM — Password Policy and MFA).
- Q058 — **A** — **Model B**: AWS provides the **key storage** layer — keys live in the AWS environment (**CloudHSM**) and are "inaccessible to any AWS employee" — and the customer supplies the **KMI** and manages the **encryption algorithm** and **key management**, talking to CloudHSM over **SSL**. The mirror-image split is Model A (customer manages encryption + key storage + key management); "AWS provides everything — transparent server-side encryption" is **Model C**. Note the module uses the acronym "KMI" on pp. 118–119 and never expands it anywhere in the module (Module 12 · §12.4 AWS Encryption — Data at Rest).
- Q059 — **B** — **GCP-managed keys** "cannot be downloaded or automatically rotated" and are "used within **two weeks**," being utilized by GCP services such as **App Engine** and **Compute Engine**; **user-managed keys** are created, downloaded and managed by the user and "**expire after ten years**." A inverts both properties, C makes both types user-downloadable with one expiry, and D is backwards — key rotation is the section's own subject and applies to the user's keys. Separately: the demonstrated rotation commands are `gcloud kms keys` (Cloud KMS key versions), so the rotation mechanism is not shown acting on service-account keys themselves (Module 12 · §12.6 GCP Service Account Key Rotation).
- Q060 — **D** — Azure RBAC supports four principal types — **user · group · service principal · managed identity** (managed identity splitting into *user-assigned* and *system-assigned*) — and assigns roles at the **subscription**, **resource group** or **single resource** scope. C keeps the principals right but substitutes tenant/management-group, which are only the categories the walkthrough *searches* at step 1, not scopes a role is assigned at; B is correct on scope but omits managed identity; A omits service principals and managed identity outright. Custom roles are created only "when the built-in roles do not meet the requirements of the organization" (Module 12 · §12.5 Azure RBAC).

## Module 13
- Q061 — **C** — Table 13.2's integrity row runs **WEP CRC-32 · WPA Michael algorithm and CRC-32 · WPA2 CBC-MAC · WPA3 BIP-GMAC-256**. Every option is a permutation of the same four values, so the row has to be recalled exactly. Two memory hooks: WEP and WPA are the only two schemes whose integrity check is a **checksum** (CRC-32, optionally paired with Michael), while WPA2 and WPA3 use **true MAC-based** mechanisms (CBC-MAC, BIP-GMAC-256) — and **Michael + CRC-32 belongs to WPA, never to WPA2** (Module 13 · §13.2 WEP vs WPA vs WPA2 vs WPA3).
- Q062 — **D** — The core rule is a **comparison against the inventory**: "The detected wireless APs are compared with the wireless device inventory for the environment. If an AP that is not listed in the inventory is found, it can generally be considered as a rogue AP." The inventory is therefore not bookkeeping — it is the detection mechanism (an AP absent from the inventory *is* the finding). SSID matching and hidden-SSID state are irrelevant to the test, and weak encryption is a weakness, not the definition of rogue (Module 13 · §13.4 Detecting and Locating Rogue Access Points).
- Q063 — **A** — The module quantifies failure two ways: an AP broadcasting **1500-byte** packets at **11 Mb/s** exhausts the whole IV space in **five hours**, and roughly **24 GB** of reconstructed key stream permits **real-time** decryption. Both stem from the same root cause — the **24-bit IV is too small and is sent in the cleartext portion of the message**, so a busy AP recycles values and keystream reuse follows. Note the module *also* prints "all **224** available IV values" on p39 and never squares that with the five-hours figure or with 2^24; use the five-hours figure, which is the one stated as a duration (Module 13 · §13.2 Issues in WEP, WPA and WPA2).
- Q064 — **B** — Two issues are printed only under WPA2: the **wireless denial of service** — attackers "exploit WPA2 replay-attack detection to send forged group-addressed data frames with a large PN" — and **Wi-Fi protected setup PIN recovery**, which lets an attacker disclose the WPA2 key from the WPS PIN. A is the **WPA** issue set (insecure-RNG GTK predictability plus TKIP IP guessing); C and D are **WEP** issues (IV-collision known-plaintext and dictionary attacks; CRC-32 integrity and the cleartext IV). Both WPA2 items are notable because neither has a WEP or WPA counterpart anywhere in the module (Module 13 · §13.2 Issues in WEP, WPA and WPA2).
- Q065 — **D** — The printed order is **WPA3 → WPA2 Enterprise with RADIUS → WPA2 Enterprise → WPA2 PSK → WPA Enterprise → WPA → WEP**. The two easy slips are (1) putting **WPA2 PSK above WPA Enterprise**, which the source does not do — Enterprise sits fourth and PSK third; and (2) demoting **WPA3**, which the source ranks first, ahead of both WPA2 Enterprise modes. Caveat: this is the *encryption mode* list on p56; the *Wi-Fi security method* list on the same page is a different seven-item ranking in which **WEP is 6th, not 7th**, and "Open Network (no security at all)" appears only in that second list. The two lists disagree with each other and the source attaches no reason to any rank (Module 13 · §13.4 Selecting a Strong Wireless Encryption Mode).

## Module 14
- Q066 — **D** — The printed **illegal** conditions are: SYN and FIN both set (variants add PSH or RST) · only a FIN flag · all six flags unset · source or destination port zero · ACK set with a zero acknowledgement number · only the SYN bit with any other data present · a broadcast destination address ending in 0 or 255 · either reserved-for-future-use bit set. "Only the SYN bit with any other data present" is the seventh of those. A, B and C are all drawn from the page's **normal** usage list, where "FIN ACK and ACK are used in terminating a connection", "RST and RST ACK quickly end an on-going connection", and "PSH FIN and ACK may also be used initially in the same process" — note the page prints `SIN FIN` (not `SYN FIN`) on p18 (Module 14 · §14.3 Suspicious Traffic Signature Categories).
- Q067 — **C** — Table 14.2 gives UBA actor coverage as "**human actors or malware**" and UEBA's as "**malware, human actors, or machine actors**" — UEBA adds the **machine actors** — while UBA gives "**limited visibility into network activity**" and UEBA "**more visibility into network activity and context for threat investigation and response**". The whole item turns on reversing the two axes independently: A keeps the right actors but pairs them the wrong way round, B gets the actors right and reverses visibility, D denies the actor difference altogether and falls back on the data-source axis (UBA "relies on event logs", UEBA "integrates data from multiple sources"). Caveat: p113 says UBA "cannot integrate with existing security systems", which p99 contradicts (Module 14 · §14.6 UBA vs UEBA and Module Summary).
- Q068 — **B** — **Data collection → baseline establishment → anomaly detection → alert generation → alert correlation → incident investigation → response and mitigation**. A swaps detection with correlation (steps 3 and 5); C starts at baseline and renames the last two steps; D swaps establishment with detection and puts mitigation before investigation. The order is logically forced — you cannot detect an anomaly, let alone correlate alerts, before the baseline exists, and "response and mitigation" is necessarily last (Module 14 · §14.6 Network Anomaly Detection and Baseline Establishment).
- Q069 — **C** — "If the UDP port is open, the target accepts the packet and **sends no response**. If it is closed, an ICMP packet is sent in response" — printed as **ICMP Type-3 Code-3**. So the silent port is the *open* one, and "UDP scanning is more difficult to probe than TCP scanning because it does not depend on the acknowledgements received; a UDP scan instead gathers all the ICMP errors received from closed ports." A is the closed-port response plus the wrong reason, B and D are TCP semantics (RST and the three-way handshake) that cannot apply to a connectionless protocol (Module 14 · §14.4 SYN/FIN DDoS, UDP Scan and Password Cracking Traffic).
- Q070 — **D** — "In passive OS fingerprinting the attacker does not send any packets in the traffic" — so, per the page, "it is very difficult to detect a passive fingerprinting attempt, and **firewalls or other security devices cannot detect passive OS fingerprinting** either. The defender must detect these attempts manually with the help of packet sniffing tools." The five fields are the **initial TTL, the do-not-fragment flag, the maximum segment size, the window size, and the selective ACK (SACK) OK**. C describes **active** ICMP fingerprinting — the probes it lists are the ICMP-based *active* set (timestamp 13, information 15, address mask 17), which is the intended trap; B's TTL-traverses-two-routers remark is a real point the page makes, but as a secondary difficulty, not the primary one, and its field list is TCP-sequence fields rather than the printed five (Module 14 · §14.4 OS Fingerprinting).

## Module 15
- Q071 — **D** — —The events at level 0 are of the greatest importance and those at level 7 are of least importance, and the router section states the rule outright: —The lower severity number represents a higher severity and vice-versa.— The printed order of names is emergency, alert, critical, error, warning, notification, informational, and debugging. A and C are the same assertion with the scale inverted, which is the intended trap; B fails because the module does attach numbers to the names — it simply does not do so consistently, printing the number beside the name in the Linux, router and ASA tables but printing level 0 as the letter —O{O} in the firewall and router prose, leaving the Emergency value cell blank in the p43 table, and printing **no numeric column at all** in Table 15.21 (Module 15 { **p60 Firewall Logging{pR}, p91 NB Table 15.12{pR}; 15-LO05a, 15-LO03b, 15-LO06a, 15-LO08d).
- Q072 — **C** — —In a push-based mechanism, the system or application either saves records on the local disk or sends them over the network. If the records are being sent over the network, then a log collector is needed to collect them. System Logging Protocol (syslog) and Simple Network Management Protocol (SNMP) are the two main push-based protocols through which log records are transferred.— Pull is the mirror image: —a system or an application pulls the log records from a log source. It works based on the client–server model. The system or device that follows this mechanism usually stores their log data in a proprietary format. For example, Check Point provides OPSEC C library to pull logs from a Check Point device.— A swaps the two mechanisms outright, B claims both mechanisms use the same two protocols (nothing in the page says a protocol can be initiated by either end), and D is doubly wrong — Windows Event Viewer is a *viewer*, and SNMP is named as push-based (Module 15 { **p6 Typical Log Sources{pR}; 15-LO01a).
- Q073 — **D** — —In centralized logging, logging, monitoring, and analysis of logs are performed through a series of steps.— The figure on p121 prints all seven in order: **Log Collection — Log Transmission — Log Storage — Normalization — Log Correlation — Log Analysis — Alerting and Reporting**. A swaps Normalization and Storage, B swaps Storage and Transmission, and C swaps Correlation and Analysis — correlation is defined as matching normalized data to —determine a set of related events based on a certain set of rules,— which has to precede the analysis that interprets them. Worth knowing for exam-writers: the p152 Module Summary enumerates **eight** steps because it splits the final step into —alerting,— and —reporting,— while the body numbers seven and p145's heading prints —Step 7: Alerting and Reporting— as one step. Both printed forms are kept and the difference is not reconciled (Module 15 { **pp121–122 Centralized Logging, Monitoring, and Analysis Process{pR}, p152 Module Summary; 15-LO08c, 15-LO08g).
- Q074 — **D** — —The IIS log file format is fixed, has commas as separators, and uses local time. The NCSA Common format is fixed, has spaces as separators, and uses local time.— The page adds the scope limit that makes the item: NCSA is —used for websites and not for FTP sites.— A takes the —not for FTP sites— clause and attaches it to IIS instead of NCSA, and also mis-sets NCSA's clock to UTC; B has both the separators and the time sources exchanged; C reverses the two formats wholesale. Note that the page prints the date two different ways in the same example — —03/6/11— in the log line against —03/06/2011— in the table's —Appear as— cell — and both are kept as printed (Module 15 { **p103 Table 15.16{pR}; 15-LO07b).
- Q075 — **C** — —Micro-level correlation: It correlates fields within a single event or set of events. It is also known as atomic correlation. Micro-level correlation is performed only when raw event data is normalized. It is further divided into field correlation and rule correlation.— —Macro-level correlation gains information from rule correlation, vulnerability correlation, profile (fingerprint) correlation, anti-port correlation, watch list correlation, and geographic location correlation to validate and gain intelligence on the event stream.— A exchanges the two. B keeps the micro-level half exactly right and then asserts the opposite for macro-level, which must run *on* normalized data — that is the input correlation consumes. D denies micro-level exists. Caveat worth flagging rather than hiding: the page **names six** macro-level inputs but gives prose descriptions for only **three** — vulnerability, profile (fingerprint) and anti-port. Watch list correlation and geographic location correlation are named with no description anywhere in pp140–141, and nothing was supplied for them from outside the module (Module 15 { **p140 Step 5: Log Correlation{pR}; 15-LO08f).

## Module 16
- Q076 — **D** — The printed methodology runs: **obtain a search warrant** (before investigating suspects) — **evaluate and secure the scene** (before collecting) — **collect the evidence** (neglect nothing) — **secure the evidence** (loss weakens the case) — **acquire the data** (finds the reason for the intrusion) — **analyze the data** (the most important phase, via log monitoring) — **assess the evidence and the case** — **prepare the final report** (investigator's AND suspect's actions) — **testify as an expert witness**. A starts at the scene and scrambles the middle; B collects before securing the scene and testifies before reporting; C acquires before collecting and secures after analyzing (Module 16 –16.9 Typical Forensics Investigation Methodology; 16-LO09b).
